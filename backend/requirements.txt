# Bornes hautes posées volontairement.
#
# Ce fichier n'avait que des `>=`. Constat mesuré le 5 août 2026, en demandant
# à PyPI ce que chaque ligne installe réellement aujourd'hui :
#
#   pandas>=2.0.0        →  3.0.5     (saut de majeure)
#   numpy>=1.24.0        →  2.5.1     (saut de majeure)
#   bcrypt>=4.0.0        →  5.0.0     (saut de majeure)
#   cryptography>=42.0.0 →  50.0.0    (huit majeures d'écart)
#   paramiko>=3.4.0      →  5.0.0     (saut de majeure)
#
# Autrement dit : deux `docker compose up --build` à trois mois d'écart ne
# donnaient pas la même application, et une CI verte ne disait rien de ce qui
# tournerait ensuite. Une majeure a le droit de casser — c'est exactement ce
# que le numéro annonce — donc la borne haute transforme « ça a cassé en prod
# un mardi » en « la montée de version est un ticket qu'on ouvre quand on
# décide ».
#
# La règle appliquée : **plafonner à la majeure suivant celle qui est déjà
# publiée**, pas en dessous. Comme la CI installait le plus récent, c'est cette
# majeure-là qu'elle exerçait déjà ; descendre plus bas reviendrait à changer
# le comportement testé au lieu de le figer. Une inspection du code n'a
# d'ailleurs relevé aucun appel retiré par pandas 3 (`applymap`, `iteritems`,
# `DataFrame.append`), aucun `inplace=True` et aucune affectation chaînée —
# les trois choses qui cassent au passage au copy-on-write.
#
# Ces bornes restent un filet, pas un verrou. Le verrou, c'est un lockfile :
#
#   pip install pip-tools
#   pip-compile requirements.txt -o requirements.lock   # hachages inclus
#   pip-sync requirements.lock                          # en CI et dans l'image
#
# La CI installe alors le .lock — exactement ce qui a été testé — et ce
# fichier ne sert plus qu'à décrire l'intention.
